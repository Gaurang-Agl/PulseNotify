Executive Technical Overview & Domain Problem

⚠️ The Real-World Volatility Problem

Airlines employ aggressive dynamic revenue management algorithms that recalculate seat fares dozens of times daily. Fares between high-density corridors (such as DEL-BOM) fluctuate rapidly from ₹6,200 to ₹4,100 during low site traffic and surge back to ₹9,800 within hours.

  • Human travelers cannot refresh search pages 24 hours a day.
  • Discount windows close before manual discovery occurs.
  • Naive monitoring systems crash external APIs with duplicate queries.
✨ The PulseNotify Engineering Solution

PulseNotify mirrors the core monitoring engines behind Google Flights and Skyscanner by providing an automated, decoupled, event-driven flight intelligence system.

  • Sub-second REST Gateway: Users register threshold alerts without blocking on third-party airline calls.
  • Instant Ingestion & 30s Clock: Event-driven instant alert evaluation upon price drop, plus synchronized 30s Celery Beat background polling.
  • Shared Redis Price Cache: 30-second snapshot TTL ensures the frontend Flight Radar and background worker evaluate the exact same ticket price.
  • On-Demand Force-Refresh: Travelers can tap 'Scan Now' to bypass the 30s Redis cache via ?refresh=true, fetching fresh fluctuating fares immediately.
  • Multi-Alert Route Tagging & Tiered Triggering: Multiple alerts on the same route display aggregated count badges; when prices plunge, each alert triggers independently with separate savings calculations.
  • Route Deduplication: Aggregates distinct routes so 1,000 users watching DEL-BOM trigger only 1 external query.
  • Spam Prevention: State-machine automatically transitions triggered alerts from Active to Triggered.

Relational Database Schema (ERD)

Alert Lifecycle State Machine

stateDiagram-v2 [*] --> ACTIVE : User creates alert (POST /api/alerts/) ACTIVE --> TRIGGERED : Price <= threshold (Instant Hook / Beat) ACTIVE --> INACTIVE : User deactivates (DELETE /api/alerts/id/) TRIGGERED --> INACTIVE : User deactivates (DELETE /api/alerts/id/) TRIGGERED --> [*] : Complete (No duplicate spam) INACTIVE --> [*] : Soft deleted
Why this state machine matters:

1. Zero Spam: Moving from ACTIVE to TRIGGERED ensures the user receives exactly 1 notification even if the fare stays below the threshold for hours.

2. Soft Delete: Setting INACTIVE preserves foreign key references in historical notification logs.

3.2 Dual-Trigger Evaluation Architecture (Instant Hook + 30s Celery Beat)

Path A: Instant Ingestion Hook

When any client or radar query hits GET /api/flights/price/, evaluate_alerts_for_price() runs synchronously on fare arrival. Matching alerts trigger within 0 milliseconds.

Path B: Celery Beat 30s Fallback

Celery Beat acts as an autonomous clock, firing check_prices every 30.0 seconds. It aggregates all active routes and guarantees background evaluation even when no users are active.

Redis 7: Single Source of Truth

Prices are cached under pulsenotify:flight_price:{ROUTE} with TTL=30s. Both instant searches and Celery workers query the identical fare snapshot.

The 4 Critical Engineering Pillars for Resilient Distributed Systems

Pillar 1 O(N) -> O(1) Optimization

High-Efficiency Route Aggregation

If 1,000 travelers set alerts for DEL-BOM, querying airline APIs 1,000 times per minute would breach rate limits within minutes. PulseNotify optimizes this with database route deduplication: 

active_alerts = PriceAlert.objects.filter(status=PriceAlert.Status.ACTIVE)
routes = active_alerts.values_list('origin', 'destination').distinct()

Queries the external feed once per unique route, then evaluates all 1,000 user thresholds in-memory. Zero wasted API credits.

Pillar 2 Idempotency & Anti-Spam

Atomic State Transitions

When a price drops below a threshold, the Celery worker dispatches send_notification and atomically transitions the alert status from ACTIVE to TRIGGERED: 

NotificationLog.objects.create(alert=alert, triggered_price=price, ...)
alert.status = PriceAlert.Status.TRIGGERED
alert.save()

Subsequent 30-second polling loops only evaluate ACTIVE alerts. Travelers never receive repetitive notification floods.

Pillar 3 Rate-Limit Telemetry

API Quota Milestone Trapping

Third-party airline APIs enforce strict monthly call limits. PulseNotify records external consumption in PostgreSQL and evaluates milestone traps at:

25% 50% 60% 70% 80% 90% (Critical)

Triggers real-time banners on the frontend, giving operators early runway to upgrade quotas before system outages occur.

Pillar 4 Tenant Security

Multi-Tenant Scoping & RBAC

Every user action is authenticated via JWT tokens. QuerySets are strictly scoped at the ORM layer: 

def get_queryset(self):
    return PriceAlert.objects.filter(user=self.request.user)

If User B requests User A's alert ID, the API returns 404 Not Found rather than 403 Forbidden, preventing ID enumeration attacks.

Executive System Pitch & Master Technical FAQ

🎯 The 60-Second Elevator Pitch (STAR Framework)

"PulseNotify is a distributed, event-driven flight price monitoring and telemetry system built to replicate the tracking engines behind Google Flights and Skyscanner. Travelers register threshold alerts, and our system autonomously monitors airline fares without blocking user threads.

To prevent API rate-limit exhaustion, I architected a route aggregation engine in Celery that queries distinct routes once per cycle, optimizing queries from $O(N) \to O(1)$. When a fare drops below budget, Celery workers dispatch asynchronous notifications and atomically transition alerts to 'Triggered' to eliminate notification spam.

I also engineered third-party API quota milestone tracking with telemetry warnings at 25%, 50%, and 80%, full multi-tenant row-level isolation, and an interactive React dashboard with zero-CORS proxying."

Q1: Why choose Celery Beat instead of Linux cron jobs or standard Python sleep loops?

Answer: In-process loops like time.sleep() inside web threads freeze application workers, waste memory, and die if the process restarts. Linux cron jobs lack centralized task queues, dead-letter retries, and distributed monitoring. Celery Beat acts as a dedicated clock process that publishes task messages to a centralized Redis broker. This decouples scheduling from execution: worker nodes can scale horizontally, recover gracefully from node failures, and absorb burst traffic without packet loss.

Q2: What happens if 10,000 travelers monitor DEL-BOM at the same time?

Answer: PulseNotify handles this via database route deduplication. Our Celery task runs active_alerts.values_list('origin', 'destination').distinct(). Even if 10,000 alerts exist for DEL-BOM, the flight provider endpoint is queried exactly once. The resulting price is evaluated against all 10,000 threshold values in memory in milliseconds. This protects API rate limits and reduces external costs by 99.9%.

Q3: How do you prevent users from receiving 100 notifications if a flight stays cheap all day?

Answer: We implemented a three-stage state machine: ACTIVE, TRIGGERED, and INACTIVE. When a price condition is met, the worker writes the NotificationLog and atomically transitions the alert status from ACTIVE to TRIGGERED in the same transaction. The recurring 30-second Celery Beat task and instant price-ingestion triggers strictly query status='active', so triggered alerts are never re-evaluated unless reactivated.

Q4: Why choose PostgreSQL over a NoSQL document database like MongoDB?

Answer: Flight price monitoring demands strict relational integrity and ACID guarantees. Foreign keys linking Users -> PriceAlerts -> NotificationLogs guarantee that notifications cannot exist without valid alerts. Furthermore, PostgreSQL's relational query engine allows for fast aggregations, such as computing the Top Routes Leaderboard via values('origin','dest').annotate(count=Count('id')) and enforcing row-level tenancy without custom document joins.

Q5: How is security handled between ordinary travelers and platform administrators?

Answer: We enforce Role-Based Access Control (RBAC) across two tiers. Standard users are assigned role: 'user'. Views like AdminSummaryView and Quota Telemetry enforce custom permission class IsAdminUser, returning HTTP 403 Forbidden to normal users. On the frontend, if a user lacks the admin role, the React interface displays an explicit RBAC Lock screen with terminal elevation instructions.

Q6: If a user has two alerts on DEL-BOM (one for ≤₹4,000 and one for ≤₹3,500) and the price drops to ₹3,200, what happens?

Answer: Both alerts trigger independently. The evaluation engine identifies all active alerts whose threshold is greater than or equal to ₹3,200. Because both ₹4,000 and ₹3,500 satisfy the condition, the system enqueues two separate send_notification.delay(alert_id, price) Celery tasks. Each task generates its own NotificationLog entry with individual savings calculations (₹800 savings for the ₹4,000 alert and ₹300 savings for the ₹3,500 alert) and transitions each alert atomically to TRIGGERED. On subsequent 30-second cycles, neither alert triggers again due to anti-spam idempotency.

Q7: Why specify --pool=solo for Celery workers on Windows?

Answer: Windows does not support the POSIX fork() system call, which is Celery's default execution mechanism on Linux. Running Celery without --pool=solo on Windows causes multiprocessing deadlocks, task hanging, and file descriptor permission errors. The solo pool executes tasks in-process within a single thread, providing complete reliability during local development while maintaining full Redis queue semantics.
